## ⚠️ مبدأ حاكم

> **الإصدار ليس "رفع كود"، بل هو عقد مُسلَّم.** كل إصدار في MOTANAQIL هو حزمة مكتملة، مُختبَرة، موثّقة، موقّعة، وقابلة للتثبيت والتراجع، تُسلَّم لصاحب المشروع بصيغة موحّدة (`Release-vX.X.X.zip`). لا يُعتبر أي عمل "منتهياً" حتى يُغلَف بإصدار رسمي يمرّ عبر بوابات الجودة (Quality Gates) ويحصل على توقيع القبول (Sign-off). الإصدارات تُبنى آلياً، تُوقَّع رقمياً، وتُحفظ كأثر دائم لا يُمس.

## 1. فلسفة الإصدارات والمبادئ

### 1.1 المبادئ الحاكمة

| المبدأ | التطبيق في MOTANAQIL |
|--------|---------------------|
| **Release = Contract** | كل إصدار حزمة مُسلَّمة بمحتوى ثابت ومُوقَّع، لا "نسخة على الخادم فقط" |
| **Reproducible** | نفس الـ commit + نفس الإعدادات → نفس الحزمة bit-for-bit |
| **Immutable** | الإصدار المُعلن لا يُعدَّل أبداً؛ الإصلاح = إصدار جديد |
| **Atomic** | الإصدار وحدة كاملة؛ لا "نصف ميزة" في إصدار رسمي |
| **Traceable** | كل إصدار مربوط بـ commit, tag, build, sign-off, CHANGELOG |
| **Reversible** | كل إصدار قابل للتراجع خلال دقائق (RTO مُقاس) |
| **Gated** | لا إصدار بدون اجتياز كل بوابات الجودة + توقيع |
| **Documented** | لا إصدار بدون CHANGELOG + Release Notes + تحديث الوثائق |

### 1.2 ما يُعتبر "إصداراً رسمياً"

```typescript
const officialReleaseDefinition = `
الإصدار الرسمي هو كل بناءٍ يستوفي *جميع* الشروط التالية معاً:
  1. له tag موقّع في Git بصيغة vX.Y.Z (أو vX.Y.Z-pre.N).
  2. اجتاز كل Quality Gates (قسم 7) على CI.
  3. أُنتجت له حزمة Release-vX.Y.Z.zip كاملة (قسم 6).
  4. له إدخال في CHANGELOG.md و Release-Notes.pdf.
  5. له توقيع قبول (Sign-off) من صاحب المشروع للإصدارات MAJOR/MINOR.
  6. رُفعت الحزمة لمستودع الإصدارات (قسم 12) مع checksum.
ما دون ذلك (build على develop، preview، nightly) = "بناء" وليس "إصداراً".
`;
```

## 2. Semantic Versioning بالتفصيل

### 2.1 الصيغة

```
v MAJOR . MINOR . PATCH [ - PRE_RELEASE ] [ + BUILD_METADATA ]
        │       │       │         │                  │
        │       │       │         │                  └─ رقم البناء/commit (لا يؤثر على الأسبقية)
        │       │       │         └─ alpha / beta / rc.N
        │       │       └─ إصلاحات، لا تغيير واجهات
        │       └─ ميزات جديدة متوافقة رجعياً
        └─ تغييرات غير متوافقة رجعياً (Breaking)
```

### 2.2 متى نرفع كل رقم (قواعد MOTANAQIL)

```typescript
const versionBumpRules = {
  MAJOR: [
    'تغيير Breaking في API العام (حذف/تعديل endpoint أو response shape)',
    'تغيير Breaking في schema قاعدة البيانات لا يمكن هجرته بسلاسة',
    'إعادة هيكلة معمارية كبرى تغيّر حدود الـ modules',
    'تغيير في نموذج البيانات (Domain Model) يكسر التكاملات',
    'مثال من المشروع: v1.2.0 → v2.0.0 عند Maps Integration لأنه يضيف',
    '  بنية جديدة (تتبع فوري + geofencing + PostGIS) تغيّر عقد الطلب',
  ],
  MINOR: [
    'ميزة جديدة متوافقة رجعياً (endpoint جديد، حقل اختياري جديد)',
    'صفحة/قسم جديد في الواجهة',
    'تحسين داخلي مرئي للمستخدم لا يكسر شيئاً',
    'مثال: v2.0.0 → v2.1.0 عند Administration Panel (ميزات جديدة)',
  ],
  PATCH: [
    'إصلاح خطأ (bug fix)',
    'تحديث أمني dependency',
    'تحسين أداء بدون تغيير سلوك',
    'تصحيح وثائق/ترجمات',
    'مثال: v2.1.0 → v2.1.1 لإصلاح خطأ في حساب المسافة',
  ],
  PRE_RELEASE: [
    'alpha.N  → غير مستقر، للمطورين فقط، قد يتغير يومياً',
    'beta.N   → مستقر الميزات، لاختبار القبول، قد يحتوي أخطاء',
    'rc.N     → Release Candidate، مطابق للإصدار المرشح، للاختبار النهائي',
  ],
  BUILD_METADATA: [
    '+build.20260724.sha1a2b3c → للتتبع فقط، v1.0.0+build.1 == v1.0.0+build.2',
  ],
};
```

### 2.3 قواعد الأسبقية والترقيم

```typescript
const precedenceRules = [
  '1.0.0-alpha < 1.0.0-alpha.1 < 1.0.0-beta < 1.0.0-rc.1 < 1.0.0',
  'الإصدار 0.y.z (التطوير الأولي): أي تغيير قد يكون Breaking، الواجهة غير مستقرة',
  'بمجرد الوصول لـ 1.0.0: الواجهة العامة مستقرة، وتخضع لقواعد MAJOR/MINOR/PATCH',
  'لا يُعاد استخدام رقم إصدار مُعلَن أبداً (حتى المسحوب)',
  'PATCH لا يضيف ميزات؛ MINOR لا يكسر؛ MAJOR هو الوحيد المسموح له بالكسر',
];
```

### 2.4 توثيق الـ Breaking Changes

```markdown
<!-- كل تغيير Breaking يُوثَّق في CHANGELOG تحت ## [vX.0.0] مع قسم ### BREAKING -->
### BREAKING CHANGES
- **API:** حذف `GET /v1/orders/legacy` → استخدم `GET /v1/orders`.
- **DB:** عمود `orders.legacy_status` أُزيل بعد هجرة البيانات لـ `orders.status`.
- **Migration:** شغّل `prisma migrate deploy` *قبل* نشر الكود (نمط Expand-Contract، ملف 11 §20).
- **Client:** الحد الأدنى لـ SDK أصبح v2.0.0.
```

## 3. دورة حياة الإصدار (Release Lifecycle)

### 3.1 المراحل

```
┌──────────┐  ┌──────────┐  ┌──────────  ┌──────────┐  ┌──────────┐  ┌──────────┐
│ Planning │→│ Develop  │→│  Freeze  │→│   RC &   │→│ Release  │→│  Post-   │
│          │  │          │  │          │→│  QA Gate │  │  & Sign  │  │ Release  │
└──────────  └──────────┘  └──────────┘  └──────────┘  └──────────  └──────────┘
   نطاق +        ميزات على     تجميد        بناء RC +     tag موقّع +    مراقبة +
   تقدير +       feature       الميزات +    اختبارات +    حزمة +         hotfixes +
   تذكرة         branches      إصلاحات      بوابات        sign-off +     retrospective
   رئيسية                     فقط           الجودة        نشر
```

### 3.2 تفصيل كل مرحلة

```typescript
const releaseLifecycle = {

    rule: 'كل تذكرة في النطاق تُربط بـ milestone الإصدار في GitHub',

  develop: {

  freeze: {

    action: 'إنشاء release/vX.Y.Z من develop',
    allowed: 'إصلاحات الأخطاء (bugfix) + وثائق فقط',
    forbidden: 'ميزات جديدة (تُرحَّل للإصدار التالي)',
  },

  rc_and_qa: {
    builds: ['vX.Y.Z-rc.1', 'rc.2', ...],
    activities: [
      'نشر على staging (مطابق للإنتاج)',
      'تنفيذ خطة الاختبار (10-Testing-Strategy)',

  },

  release_and_sign: {
    actions: [
      'دمج release/vX.Y.Z في main عبر merge commit',

      'بناء الحزمة النهائية آلياً (قسم 16)',
      'توليد CHANGELOG + Release-Notes.pdf',
      'رفع الحزمة لمستودع الإصدارات (قسم 12)',
      'sign-off من صاحب المشروع (قسم 18) لـ MAJOR/MINOR',
      'نشر للإنتاج عبر 11-Deployment (Blue-Green)',
    ],
  },

  post_release: {
    duration: '48 ساعة مراقبة مكثفة + أسبوع مراقبة عادية',
    activities: [
      'مراقبة error rate / latency / conversions',
      'إغلاق milestone',
      'دمج main → develop (لالتقاط أي hotfix)',

      'تحديث 00.04-Revision-History',
    ],
  },
```

## 4. استراتيجية الفروع للإصدارات

### 4.1 الفروع وأدوارها

```
main            ← تاريخ الإنتاج فقط؛ كل commit = إصدار مُعلَن؛ tags موقّعة
develop         ← رأس التطوير؛ متكامل دائماً؛ يبني nightly
release/vX.Y.Z  ← فرع تجميد؛ يعيش من freeze حتى release؛ يُحذف بعد الدمج
hotfix/vX.Y.Z   ← من main؛ إصلاح طارئ؛ يُدمج في main و develop معاً
feature/*       ← من develop؛ عمر قصير
bugfix/*        ← من develop (أو release/* إن كان للإصدار المجمَّد)
```

### 4.2 قواعد الدمج للإصدارات

```typescript
const mergeRules = {
  'feature → develop': 'squash merge؛ يحذف الفرع',
  'develop → release/*': 'merge commit (للحفاظ على تاريخ النطاق)',
  'release/* → main': 'merge commit + tag موقّع',
  'release/* → develop': 'merge commit (لالتقاط إصلاحات الـ freeze)',
  'hotfix/* → main': 'merge commit + tag PATCH موقّع',
  'hotfix/* → develop': 'merge commit (لمنع回归 الخطأ)',
  'main → develop': 'فقط إن وُجد فرق بعد hotfix',
};
```

### 4.3 حماية main و release/*

```yaml
# GitHub branch protection (ملخّص)
main:
  required_approvals: 2
  require_status_checks: [ci, security, e2e-smoke]
  require_signed_commits: true
  require_signed_tags: true
  no_force_push: true
  no_deletion: true
  include_admins: true

release/*:
  required_approvals: 1
  require_status_checks: [ci, regression]
  restrict_who_can_push: [release-managers]
```

## 6. حزمة التسليم الكاملة (Release Package)

### 6.1 هيكل الحزمة الإلزامي

> **هذا هو العقد.** كل إصدار يُسلَّم كـ `Release-vX.Y.Z.zip` يحوي *بالضبط* هذا الهيكل. غياب أي عنصر = الإصدار مرفوض.

```
Release-vX.Y.Z/
│
├── Source-Code/
│   ├── apps/
│   │   ├── api/                 # NestJS backend
│   │   ├── web/                 # Next.js public
│   │   └── admin/               # Next.js admin
│   ├── packages/                # types, utils, ui
│   ├── prisma/
│   │   ├── schema.prisma
│   │   ├── migrations/          # كل migrations حتى هذا الإصدار
│   │   └── seed.ts
│   ├── package.json
│   ├── package-lock.json        # لتكرار البناء bit-for-bit
│   ├── .nvmrc
```

### 11.2 آلية التوقيع

```bash
# 1. توقيع الـ git tag (GPG/SSH)
git tag -s vX.Y.Z -m "Release vX.Y.Z"   # -s = GPG signed

# 2. checksum للحزمة
sha256sum Release-vX.Y.Z.zip > Release-vX.Y.Z.zip.sha256

# 3. توقيع الـ checksum (detached signature)
gpg --armor --detach-sign --local-user "$RELEASE_KEY" Release-vX.Y.Z.zip.sha256

# 4. نشر المفتاح العام في مكان ثابت (/.well-known/release-keys.txt)
#    ليتحقق صاحب المشروع/المُثبِّت من التوقيع
gpg --verify Release-vX.Y.Z.zip.sha256.asc Release-vX.Y.Z.zip.sha256
sha256sum -c Release-vX.Y.Z.zip.sha256
```

## 16. أتمتة بناء الحزمة (Release Automation)

### 16.1 سكربت بناء الحزمة

```bash
#!/usr/bin/env bash
# scripts/build-release-package.sh
set -euo pipefail

VERSION="${1:?usage: build-release-package.sh vX.Y.Z}"
TAG="${VERSION}"
PKG="Release-${VERSION#v}"
STAGE="$(mktemp -d)"

echo "📦 Building release package for ${VERSION}"

# 0. نظافة + تحقق من الشجرة
git diff --quiet && git diff --cached --quiet || { echo "❌ working tree not clean"; exit 1; }
git rev-parse "${TAG}^{commit}" >/dev/null 2>&1 || { echo "❌ tag ${TAG} not found"; exit 1; }
git verify-tag "${TAG}" || { echo "❌ tag signature invalid"; exit 1; }

git checkout "${TAG}" --detach

# 1. Source-Code (بدون node_modules/.next/dist)
mkdir -p "${STAGE}/${PKG}/Source-Code"
git archive "${TAG}" | tar -x -C "${STAGE}/${PKG}/Source-Code"

# 2. تجميع الوثائق من docs/ (الـ MES)
mkdir -p "${STAGE}/${PKG}/Documentation"
cp -R docs/MOTANAQIL-MES "${STAGE}/${PKG}/Documentation/"
cp docs/README.md docs/CHANGELOG.md "${STAGE}/${PKG}/Documentation/"

# 3. Database
mkdir -p "${STAGE}/${PKG}/Database"
cp -R prisma/schema.prisma prisma/migrations prisma/seed.ts "${STAGE}/${PKG}/Database/"
pg_dump --schema-only "$PROD_READONLY_DSN" > "${STAGE}/${PKG}/Database/seed-data.sql" || true

# 4. API (OpenAPI مُولَّد من البناء)
mkdir -p "${STAGE}/${PKG}/API"
npm run build:api && npm run openapi:export > "${STAGE}/${PKG}/API/openapi.yaml"
cp docs/postman-collection.json docs/webhooks.md "${STAGE}/${PKG}/API/" 2>/dev/null || true

# 5. Build artifacts (SBOM + audit)
mkdir -p "${STAGE}/${PKG}/Build-Artifacts"
npm ci && npm ls --all --json > "${STAGE}/${PKG}/Build-Artifacts/sbom.json" || true
npm audit --json > "${STAGE}/${PKG}/Build-Artifacts/dependency-audit.json" || true
echo "${DOCKER_IMAGE_TAGS}" > "${STAGE}/${PKG}/Build-Artifacts/docker-images.txt"

# 6. Testing (تُجمع من CI artifacts)
mkdir -p "${STAGE}/${PKG}/Testing"
cp -R .ci-artifacts/testing/* "${STAGE}/${PKG}/Testing/"

# 7. Version.txt + CHANGELOG + guides (نسخ سريعة)
envsubst < scripts/Version.txt.template > "${STAGE}/${PKG}/Version.txt"
cp docs/CHANGELOG.md "${STAGE}/${PKG}/CHANGELOG.md"
cp docs/11-Deployment-Guide.md "${STAGE}/${PKG}/Deployment-Guide.md"
cp docs/install-quick.md "${STAGE}/${PKG}/Installation-Guide.md"

# 8. رزم + checksum + توقيع
( cd "${STAGE}" && zip -qr "${PKG}.zip" "${PKG}" )
( cd "${STAGE}" && sha256sum "${PKG}.zip" > "${PKG}.zip.sha256" )
( cd "${STAGE}" && gpg --armor --detach-sign --local-user "$RELEASE_KEY" "${PKG}.zip.sha256" )
mkdir -p "${STAGE}/${PKG}/SIGNATURES"
cp "${STAGE}/${PKG}.zip.sha256" "${STAGE}/${PKG}.zip.sha256.asc" "${STAGE}/${PKG}/SIGNATURES/"
git show "${TAG}" --show-signature > "${STAGE}/${PKG}/SIGNATURES/tags-signature.asc" 2>&1 || true

# 9. نقل الحزمة النهائية
mv "${STAGE}/${PKG}.zip" dist/
echo "✅ Package ready: dist/${PKG}.zip"
```

## ⚠️ تذكير حاكم

> **إصدار بدون حزمة = عمل غير منتهٍ. حزمة بدون بوابات = مخاطرة. بوابات بدون توقيع = عدم مساءلة.** الثلاثة معاً (حزمة مكتملة + بوابات خضراء + توقيع قبول) هي التعريف الوحيد لكلمة "تم" في MOTANAQIL. فريق Buytuk لا يُسلِّم كوداً "على الخادم فقط"، ولا يعتبر مرحلةً من المراحل العشر منجزةً حتى تُغلَف بإصدار رسمي يمرّ عبر هذا الملف كاملاً. أي استثناء يُوثَّق كـ hotfix أو yank، لا كقاعدة.
