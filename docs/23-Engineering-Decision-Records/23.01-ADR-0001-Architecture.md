# ADR-0001: اختيار البنية المعمارية (Modular Monolith)

**Status:** ✅ Accepted  
**Date:** 2026-07-23  
**Deciders:** فريق Buytuk (Tech Lead, Architects)  
**Consulted:** Product Owner, DevOps Lead  
**Informed:** فريق التطوير

---

## Context

مشروع MOTANAQIL هو منصة نقل أثاث تستهدف السوق السعودي، بمتطلبات:

- **نطاق:** 10 مراحل تطويرية، من Foundation إلى Enterprise
- **فريق:** 2-5 مطورين في المرحلة الأولى
- **ميزانية:** محدودة في البداية، قابلة للتوسع
- **وقت الإطلاق:** 7-8 أشهر للمرحلة الأولى (MVP)
- **متطلبات:** SEO قوي، خرائط دقيقة، إشعارات فورية، لوحة إدارة

**المشكلة:** اختيار بنية معمارية توازن بين:
- سرعة التطوير (Time-to-Market)
- قابلية التوسع (Scalability)
- سهولة الصيانة (Maintainability)
- التكلفة (Cost)

## Decision Drivers

1. **فريق صغير** — لا نحتاج تعقيد Microservices
2. **Time-to-Market** — نحتاج إطلاق سريع
3. **SEO** — Next.js SSR/ISR يتطلب بنية محددة
4. **Real-time** — تتبع السائق يتطلب WebSocket
5. **Cost** — Microservices تكلف أكثر (بنية، مراقبة، نشر)

## Considered Options

### Option 1: Modular Monolith ✅

**الوصف:** تطبيق واحد مقسم إلى modules مستقلة، كل module له حدود واضحة.

**المزايا:**
- ✅ تطوير سريع (نشر واحد، debugging سهل)
- ✅ مشاركة الكود بسهولة (packages مشتركة)
- ✅ أداء أفضل (لا network overhead)
- ✅ مناسب للفريق الصغير
- ✅ قابل للتحويل إلى Microservices لاحقاً

**العيوب:**
- ❌ قد يصبح معقداً مع النمو (لكن modules تمنع ذلك)
-  Scaling محدود (لكن نستخدم Horizontal Scaling)

### Option 2: Microservices

**الوصف:** خدمات مستقلة لكل domain (Orders, Users, Notifications, etc.)

**المزايا:**
- ✅ Scaling مستقل
- ✅ استقلالية الفرق
- ✅ Technology diversity

**العيوب:**
- ❌ تعقيد عالي (Service Discovery, API Gateway, Distributed Tracing)
- ❌ Network overhead (Latency, Reliability)
- ❌ Debugging صعب
- ❌ يحتاج فريق كبير (5+ مطورين)
- ❌ تكلفة أعلى (بنية، مراقبة)

### Option 3: Serverless (Lambda/Functions)

**الوصف:** Functions as a Service، لا إدارة خوادم.

**المزايا:**
- ✅ لا إدارة بنية
- ✅ Auto-scaling تلقائي
- ✅ Pay per use

**العيوب:**
-  Cold starts (Latency)
- ❌ Vendor lock-in (AWS Lambda)
-  محدودية (Duration, Memory)
- ❌ Debugging صعب
- ❌ غير مناسب لـ WebSocket (تتبع السائق)

## Decision Outcome

**Chosen option:** Option 1 — Modular Monolith

**السبب:**
1. **فريق صغير** — Microservices يحتاج 5+ مطورين، نحن 2-5
2. **Time-to-Market** — Modular Monolith أسرع 3-5x من Microservices
3. **SEO** — Next.js SSR/ISR يعمل بشكل أفضل مع Monolith
4. **Real-time** — WebSocket أسهل في Monolith (لا Service Discovery)
5. **Cost** — Microservices تكلف 2-3x أكثر في البنية والمراقبة
6. **قابل للتطور** — Modules واضحة تسمح بالتحويل إلى Microservices لاحقاً عند الحاجة

**البنية المختارة:**
```
apps/
├── web/          # Next.js (Public)
├── admin/        # Next.js (Admin Panel)
└── api/          # NestJS (Backend API)

packages/
── types/        # Shared Types
├── utils/        # Shared Utilities
└── ui/           # Shared UI Components
```

## Consequences

### إيجابية
- ✅ **تطوير أسرع** — 7-8 أشهر بدلاً من 12-18 شهر
- ✅ **تكلفة أقل** — بنية بسيطة، مراقبة أسهل
- ✅ **Debugging سهل** — كل شيء في مكان واحد
- ✅ **SEO ممتاز** — Next.js SSR/ISR يعمل بكفاءة
- ✅ **Real-time سهل** — WebSocket مباشر
- ✅ **قابل للتطور** — Modules واضحة تسمح بالتقسيم لاحقاً

### سلبية
- ⚠️ **Scaling محدود** — لا Scaling مستقل للـ modules (لكن Horizontal Scaling يعوض)
- ⚠️ **Deployment واحد** — فشل في module واحد يؤثر على الكل (لكن Modules معزولة تقلل الخطر)
- ⚠️ **Codebase كبير** — يحتاج انضباط في الحدود (Enforced via ESLint + Code Review)

### مخاطر
- 🔴 **Risk:** الكود يصبح "Big Ball of Mud"  
  **Mitigation:** ESLint rules (`import/no-cycle`) + Code Review صارم + Modules boundaries
- 🔴 **Risk:** صعوبة التحويل إلى Microservices لاحقاً  
  **Mitigation:** Modules معزولة + APIs واضحة + لا اعتماد دائري

## Compliance

- ✅ **ESLint:** `import/no-cycle` يمنع الاعتماد الدائري
- ✅ **Code Review:** 2 reviewers للـ modules الحرجة
- ✅ **Tests:** Integration tests لكل module boundary
- ✅ **Documentation:** كل module له README يوضح حدوده
