# ADR-0005: اختيار استراتيجية التخزين المؤقت (Redis + Multi-Layer)

**Status:** ✅ Accepted  
**Date:** 2026-07-24  
**Deciders:** فريق Buytuk (Tech Lead, Backend Lead)  
**Consulted:** DevOps Lead, Product Owner  
**Informed:** فريق التطوير

---

## Context

مشروع MOTANAQIL يحتاج تخزين مؤقت (Caching) لدعم:

- **أداء عالي** — استجابة < 200ms للـ API
- **تقليل الحمل** — تقليل Queries على قاعدة البيانات
- **Real-time** — مواقع السائقين الحية (Geospatial)
- **Sessions** — إدارة الجلسات والـ Tokens
- **Rate Limiting** — منع الإساءة

**المشكلة:** اختيار استراتيجية تخزين مؤقت توازن بين:
- الأداء (Performance)
- الموثوقية (Reliability)
- التكلفة (Cost)
- البساطة (Simplicity)

## Decision Drivers

1. **أداء** — استجابة < 200ms للـ API
2. **تقليل الحمل** — تقليل Queries على PostgreSQL
3. **Real-time** — مواقع السائقين الحية (Geospatial)
4. **Sessions** — إدارة الجلسات والـ Tokens
5. **Rate Limiting** — منع الإساءة

## Considered Options

### Option 1: Redis + Multi-Layer ✅

**الوصف:** Redis كـ Cache رئيسي مع Multi-Layer Strategy (Client, CDN, Application, Database).

**المزايا:**
- ✅ **أداء** — استجابة < 1ms للـ Cache Hits
- ✅ **Geospatial** — GeoCommands لمواقع السائقين الحية
- ✅ **Sessions** — Session Storage سريع
- ✅ **Rate Limiting** — Sliding Window Rate Limiter
- ✅ **Pub/Sub** — Real-time Events (WebSocket)
- ✅ **Multi-Layer** — Client (Browser), CDN (CloudFront), Application (Redis), Database (Query Cache)
- ✅ **موثوقية** — Redis Cluster + Sentinel

**العيوب:**
- ❌ **تعقيد** — Multi-Layer Strategy معقد
- ❌ **تكلفة** — Redis Cluster مكلف (لكن Managed Services تعوض)

### Option 2: Memcached

**الوصف:** Cache بسيط وسريع.

**المزايا:**
- ✅ **بسيط** — سهل الفهم والتطبيق
- ✅ **سريع** — أداء ممتاز
- ✅ **مجاني** — Open Source

**العيوب:**
- ❌ **لا Geospatial** — لا GeoCommands
- ❌ **لا Pub/Sub** — لا Real-time Events
- ❌ **لا Persistence** — بيانات مفقودة عند Restart
- ❌ **لا Data Structures** — فقط Key-Value

### Option 3: Database Query Cache (PostgreSQL)

**الوصف:** استخدام Cache المدمج في PostgreSQL.

**المزايا:**
- ✅ **بسيط** — لا بنية إضافية
- ✅ **مجاني** — مدمج في PostgreSQL

**العيوب:**
- ❌ **أداء محدود** — أبطأ من Redis
- ❌ **لا Geospatial** — لا GeoCommands
- ❌ **لا Pub/Sub** — لا Real-time Events
-  **لا Sessions** — لا Session Storage

## Decision Outcome

**Chosen option:** Option 1 — Redis + Multi-Layer

**السبب:**
1. **أداء** — استجابة < 1ms للـ Cache Hits
2. **Geospatial** — GeoCommands لمواقع السائقين الحية (ملف 21-Maps)
3. **Sessions** — Session Storage سريع
4. **Rate Limiting** — Sliding Window Rate Limiter
5. **Pub/Sub** — Real-time Events (WebSocket)
6. **Multi-Layer** — Client, CDN, Application, Database

**البنية المختارة:**
```
Cache Layer 1: Client (Browser Cache, Service Worker)
Cache Layer 2: CDN (CloudFront, 1 سنة للـ Static Assets)
Cache Layer 3: Application (Redis, 5 دقائق - 1 ساعة)
Cache Layer 4: Database (PostgreSQL Query Cache, Materialized Views)

Redis Usage:
  - API Responses (5 دقائق - 1 ساعة)
  - Sessions (30 دقيقة)
  - Rate Limiting (Sliding Window)
  - Geospatial (مواقع السائقين الحية)
  - Pub/Sub (Real-time Events)
  - Queue (BullMQ)
```

## Consequences

### إيجابية
- ✅ **أداء ممتاز** — استجابة < 200ms للـ API
- ✅ **تقليل الحمل** — تقليل Queries على PostgreSQL بنسبة 70-90%
- ✅ **Real-time** — مواقع السائقين الحية عبر GeoCommands
- ✅ **Sessions** — Session Storage سريع
- ✅ **Rate Limiting** — منع الإساءة
- ✅ **Pub/Sub** — Real-time Events

### سلبية
- ⚠️ **تعقيد** — Multi-Layer Strategy معقد
- ️ **تكلفة** — Redis Cluster مكلف (لكن Managed Services تعوض)

### مخاطر
- 🔴 **Risk:** Cache Stampede (Thundering Herd)  
  **Mitigation:** Cache-Aside Pattern + Mutex Locks + Stale-While-Revalidate
- 🔴 **Risk:** Cache Invalidation  
  **Mitigation:** Event-Driven Invalidation + TTL + Versioning

## Compliance

- ✅ **Performance:** Cache Hit Rate > 80%
- ✅ **Reliability:** Redis Cluster + Sentinel
- ✅ **Security:** TLS + ACL + Password
- ✅ **Monitoring:** Cache Hit Rate, Latency, Memory Usage
