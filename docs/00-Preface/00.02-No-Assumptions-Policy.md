## 1. المبدأ الأساسي

> **"لا يجوز لأي مشارك في المشروع افتراض أي متطلب، أو تغيير أي وظيفة، أو حذف أي جزء من المشروع، أو اتخاذ أي قرار تصميمي أو تقني دون الرجوع صراحةً إلى الوثائق الرسمية المعتمدة."**

### 1.1 التفسير

المشروع موثق بشكل شامل في وثائق MES (Master Engineering Specification). أي شيء **غير مذكور صراحةً** في الوثائق:

- ❌ ليس جزءاً من النطاق
- ❌ لا يجب تنفيذه
- ❌ لا يجب افتراض وجوده

إذا كان هناك **غموض** أو **نقص** أو **تعارض** في الوثائق:

- ✅ يجب التوقف الفوري
- ✅ يجب توثيق الاستفسار
- ✅ يجب انتظار الاعتماد الرسمي

## 3. القواعد الإلزامية

### 3.1 قاعدة 1: عدم الافتراض

```
❌ ممنوع:
- افتراض أن ميزة موجودة لأنها "بديهية"
- افتراض سلوك معين غير موثق
- افتراض تكامل مع خدمة خارجية بدون وثيقة
- افتراض متطلبات المستخدم بدون مصدر موثق
- افتراض معايير جودة غير محددة

✅ مسموح:
- تنفيذ ما هو موثق صراحةً فقط
- الرجوع للوثائق عند أي شك
- طلب توضيح رسمي عند الغموض
```

### 3.2 قاعدة 2: عدم الإضافة بدون موافقة

```
❌ ممنوع:
- إضافة ميزات "لأنها ستكون مفيدة"
- إضافة تكاملات غير مطلوبة
- إضافة dependencies غير موثقة
- إضافة optimizations غير مطلوبة

✅ مسموح:
- إضافة ما هو موثق في Requirements
- اقتراح إضافات عبر القنوات الرسمية (Feature Request)
- تحسينات الأداء ضمن الحدود المحددة في 24.01-Performance-Budget
```

### 3.3 قاعدة 3: عدم الحذف بدون موافقة

```
❌ ممنوع:
- حذف ميزة لأنها "معقدة"
- حذف متطلبات لاعتقاد أنها "غير مهمة"
- حذف tests لأنها "تفشل"
- حذف توثيق لأنه "غير ضروري"

✅ مسموح:
- حذف ما تم إهماله رسمياً (Deprecated)
- حذف بناءً على قرار موثق في ADR
- إزالة الكود الميت بعد موافقة Tech Lead
```

### 3.4 قاعدة 4: عدم التعديل بدون موافقة

```
❌ ممنوع:
- تغيير سلوك موثق بدون ADR
- تعديل contracts (API, DB) بدون موافقة
- تغيير معايير الجودة بدون تحديث الوثائق
- تعديل قرارات معمارية بدون Architecture Board

✅ مسموح:
- الإصلاحات (bug fixes) ضمن السلوك الموثق
- التحسينات التي لا تغير السلوك الخارجي
- تحديثات dependencies الأمنية (حسب 09 §19)
```

## 4. الإجراءات عند وجود غموض

### 4.1 خطوات الحل (إلزامية)

```
┌─────────────────────────────────────┐
│  1. التوقف الفوري                   │
│     - لا تبدأ التنفيذ               │
│     - لا تكتب كود                   │
│     - لا تتخذ قراراً                 │
└──────────────┬──────────────────────┘
               ↓
┌─────────────────────────────────────┐
│  2. البحث في الوثائق                │
│     - ابحث في MES الكاملة            │
│     - تحقق من ADRs ذات الصلة         │
│     - راجع الوثائق المرتبطة          │
└──────────────┬──────────────────────┘
               ↓
┌─────────────────────────────────────┐
│  3. إذا وُجد التوضيح               │
│     - تابع التنفيذ حسب الوثيقة       │
│     - سجّل الاستفسار للمرجع          │
└──────────────┬──────────────────────┘
               ↓ (إذا لم يوجد)
┌─────────────────────────────────────┐
│  4. توثيق الاستفسار                 │
│     - افتح Issue في GitHub           │
│     - املأ Clarification Template    │
│     - ضع Label: needs-clarification  │
└──────────────┬──────────────────────┘
               ↓
┌─────────────────────────────────────┐
│  5. انتظار الاعتماد                 │
│     - لا تنفيذ بدون رد رسمي         │
│     - الرد يكون في Issue نفسه        │
│     - التحديث يُضاف للوثائق         │
└─────────────────────────────────────┘
```

## 10. الأسئلة الشائعة (FAQ)

### 10.1 ما الفرق بين الافتراض والاستنتاج؟

**الافتراض (Assumption):** قبول شيء كحقيقة بدون دليل موثق  
**الاستنتاج (Inference):** استخلاص نتيجة منطقية من حقائق موثقة

- ❌ **افتراض:** "المستخدم يتوقع إشعاراً عند اكتمال الطلب" (غير موثق)
- ✅ **استنتاج:** "بناءً على REQ-190 و19-Notifications-System §4، يجب إرسال إشعار"

### 10.2 ماذا لو وجدت أن الوثيقة خاطئة؟

1. **لا تتجاهل الخطأ** وتنفذ ما تعتقد أنه صحيح
2. **افتح Issue** في GitHub مع وصف الخطأ
3. **اقترح التصحيح** مع مبررات واضحة
4. **انتظر الاعتماد** من Tech Lead
5. **بعد الاعتماد:** نفّذ التصحيح وحدّث الوثيقة

### 10.3 ماذا لو تعارضت وثيقتان؟

```
الأولوية:
1. 00.02-No-Assumptions-Policy (هذا الملف)
2. 02-Business-Requirements
3. 03-System-Requirements
4. 04-Technical-Architecture
5. 09-Security
6. باقي الوثائق حسب رقمها
```

في حالة التعارض:
- ✅ نفّذ حسب الوثيقة الأعلى أولوية
- ✅ افتح Issue لتوثيق التعارض
- ✅ اقترح حلاً لتحديث الوثيقة الأقل أولوية

### 10.4 هل يمكنني اقتراح ميزات جديدة؟

**نعم!** لكن عبر القنوات الرسمية:
1. افتح Issue في GitHub مع Label: `feature-request`
2. استخدم Feature Request Template
3. اربط الطلب بأهداف المشروع (02-Business-Requirements)
4. انتظر الاعتماد من Product Owner
5. بعد الاعتماد، تُضاف الميزة للوثائق ثم تُنفّذ

### 10.5 ماذا لو كان العميل يطلب شيئاً غير موثق؟

- ❌ لا تنفّذ طلب العميل مباشرة
- ✅ وجّه العميل للقنوات الرسمية (Product Owner)
- ✅ افتح Issue لمتابعة الطلب
- ✅ انتظر الاعتماد والتوثيق قبل التنفيذ

## ⚠️ تذكير نهائي

> **"الوثائق هي العقد. الكود هو التنفيذ. الافتراض هو الخطأ."**
