## ⚠️ مبدأ حاكم

> **كل متطلب يجب أن يكون قابلاً للتتبع من المصدر إلى الاختبار.** إذا لم يكن المتطلب مربوطاً بـ DB Table + API Endpoint + UI Page + Test Case، فهو غير مكتمل. هذا الملف هو **العقد النهائي** بين المتطلبات والتنفيذ، ويُحدّث مع كل تغيير في المتطلبات أو الكود.

## 1. كيفية استخدام المصفوفة

### 1.1 بنية الصف

كل متطلب في المصفوفة يحتوي على:

| الحقل | الوصف | مثال |
|------|------|------|
| **REQ-ID** | معرف فريد للمتطلب | REQ-001 |
| **Category** | الفئة (Auth, Orders, etc.) | Auth |
| **Requirement** | وصف المتطلب | تسجيل مستخدم جديد |
| **Priority** | الأولوية (P1-P4) | P1 |
| **DB Tables** | الجداول المرتبطة | users, sessions |
| **API Endpoints** | الـ endpoints المرتبطة | POST /auth/register |
| **UI Pages** | الصفحات المرتبطة | /auth/register |
| **Test Cases** | الاختبارات المرتبطة | auth.spec.ts |
| **Status** | الحالة (Implemented/Testing/Done) | Done |

### 1.2 حالات المتطلب

- **Implemented** — الكود مكتوب
- **Testing** — قيد الاختبار
- **Done** — مكتمل ومُختبر
- **Blocked** — معطل (يحتاج توضيح)
- **Deferred** — مؤجل للمرحلة التالية

### 1.3 قواعد التتبع

```typescript
const traceabilityRules = [
  '✅ كل متطلب يجب أن يكون مربوطاً بـ DB + API + UI + Test',
  '✅ لا يُعتبر المتطلب "Done" حتى تمرّ كل الاختبارات',
  '✅ أي تغيير في المتطلب يُحدّث المصفوفة فوراً',
  '✅ لا حذف test يغطي متطلباً (13 §8)',
  '✅ المصفوفة تُراجع في كل retrospective',
];
```
