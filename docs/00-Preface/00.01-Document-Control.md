## 5. إصدار الوثائق (Versioning)

### 5.1 نظام الإصدارات (متوافق مع SemVer)

```
MAJOR.MINOR.PATCH

MAJOR: تغيير جذري يكسر التوافق مع الإصدارات السابقة
  - تغيير في بنية الوثيقة
  - حذف أقسام مهمة
  - تغيير في السياسات الأساسية

MINOR: إضافة محتوى جديد (متوافق رجعياً)
  - إضافة أقسام جديدة
  - توسيع قسم موجود
  - تحديث الأمثلة

PATCH: تصحيحات صغيرة
  - إصلاح أخطاء إملائية
  - تحديث روابط
  - توضيحات
```

### 5.2 دورة حياة الإصدار

```
Draft (مسودة) → Review (مراجعة) → Approved (معتمد) → Published (منشور)
                                                          ↓
                                                     Superseded (مُستبدل)
```

| الحالة | الوصف | من يوافق |
|--------|------|---------|
| **Draft** | قيد الكتابة، غير موثوق | المؤلف |
| **Review** | قيد المراجعة | المراجعون |
| **Approved** | معتمد، يمكن استخدامه | Tech Lead |
| **Published** | منشور رسمياً | Product Owner |
| **Deprecated** | مُهمل، لا يُستخدم في قرارات جديدة | Tech Lead |
| **Superseded** | مُستبدل بوثيقة أحدث | Tech Lead |

## 6. عملية إنشاء وتحديث الوثائق

### 6.1 إنشاء وثيقة جديدة

```markdown
## خطوات الإنشاء

1. **التخطيط:**
   - تحديد الفئة (DOC, REQ, ARC, إلخ)
   - تحديد المعرف الفريد (MQ-XXX-NNN)
   - تحديد النطاق والجمهور المستهدف

2. **الكتابة:**
   - استخدام Template القياسي
   - ملء جميع الأقسام الإلزامية
   - إضافة الأمثلة والرسوم التوضيحية

3. **المراجعة:**
   - self-review (المؤلف)
   - peer review (زميل)
   - expert review (متخصص في المجال)
   - security review (إن كانت وثيقة أمنية)

4. **الموافقة:**
   - الحصول على موافقة Tech Lead
   - توقيع صاحب المشروع للوثائق الاستراتيجية

5. **النشر:**
   - Commit برسالة واضحة
   - Tag إذا كان إصداراً رئيسياً
   - تحديث CHANGELOG.md
   - تحديث 00.04-Revision-History.md

6. **الإعلان:**
   - إبلاغ الفريق عبر القنوات الرسمية
   - تحديث الدلائل المرجعية (README, TOC)
```

### 6.2 تحديث وثيقة موجودة

```markdown
## خطوات التحديث

1. **تحديد الحاجة:**
   - خطأ مكتشف
   - تغيير في المتطلبات
   - إضافة ميزة جديدة
   - تحسين بناءً على التغذية الراجعة

2. **إنشاء فرع (Branch):**
   - `docs/update-filename-description`
   - أو `docs/fix-filename-issue`

3. **التعديل:**
   - تحديث المحتوى
   - تحديث رقم الإصدار في الـ metadata
   - إضافة إدخال في Revision History داخل الوثيقة
   - التأكد من عدم كسر الروابط الداخلية

4. **المراجعة والموافقة:**
   - نفس خطوات الإنشاء

5. **الدمج والنشر:**
   - Merge إلى main
   - Tag إذا كان إصداراً رئيسياً
   - تحديث CHANGELOG.md و 00.04-Revision-History.md
   - إبلاغ الفريق
```

### 6.3 إلغاء وثيقة

```markdown
## خطوات الإلغاء

1. **التقييم:**
   - لماذا نلغي هذه الوثيقة؟
   - هل هناك وثيقة بديلة؟
   - ما تأثير الإلغاء على المشاريع القائمة؟

2. **الموافقة:**
   - موافقة Tech Lead إلزامية
   - موافقة صاحب المشروع إذا كانت وثيقة استراتيجية

3. **الإجراء:**
   - لا نحذف الوثيقة أبداً (للحفاظ على التاريخ)
   - نغير حالتها إلى "Deprecated" أو "Superseded"
   - نضيف ملاحظة في أعلى الوثيقة توضح سبب الإلغاء
   - نُشير إلى الوثيقة البديلة (إن وُجدت)
   - نحدّث 00.04-Revision-History.md
```
